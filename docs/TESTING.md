# Testing and working in this repo

How to run the checks, how they work, and the conventions that keep the three pages working. Written in
refactor chunk 10A from the lasting parts of [`docs/refactor/LOG.md`](refactor/LOG.md), which still has the full
history (look up an entry by its chunk ID when this guide points to one).

## The checks

All dev tooling lives in `tests/` (its own `package.json`, so the site's root never has one). From the repo root:

```sh
node scripts/check-precache.mjs              # sw.js PRECACHE_ASSETS vs. what the pages load
node --test                                  # unit tests in tests/unit/ (Node 22+)
cd tests && npm ci && npm run check          # all of it: precache + unit tests + Playwright
```

| Command (in `tests/`) | Runs | In CI |
|---|---|---|
| `npm run check` | check-precache, `node --test`, then every Playwright spec | yes |
| `npm test` | Playwright only (smoke, feature specs, screenshots) | via `check` |
| `npm run unit` | unit tests only | via `check` |
| `npm run precache` | check-precache only | via `check` |
| `npm run test:update` | Playwright, rewriting screenshots that fail | no |
| `npm run compare-css` | computed-style comparison against `origin/main` (~7 min) | no, opt-in |
| `npm run pxdiff` | pixel comparison of PNG folders, or of repeated screenshot runs | no, opt-in |

- **CI:** `.github/workflows/check.yml` runs `npm run check` on every pull request and every push to `main`
  (ubuntu-24.04, Node 22, Playwright's own Chromium). When it fails, the run's `playwright-results` artifact has the
  HTML report and `test-results/`, which holds each failed screenshot's expected, actual and diff PNGs. No secrets
  are needed: the tests stub every outside request.
- **Run before pushing:** `npm run check`. CI runs it too, but a red PR costs a round trip.
- **Node 22 or newer**, and run `node --test` with no arguments (from the repo root or `tests/`). The tests import
  the app's `.js` ES modules directly, and with no root package.json Node has to detect module syntax itself.
  `node --test tests/unit/` doesn't work (Node 22 treats a directory argument as a file); for one suite use
  `node --test tests/unit/rankingsParser.test.mjs`. One Playwright spec: `npx playwright test mls-sim.spec.mjs`.
- **Chromium:** Claude Code cloud sessions have it preinstalled at `/opt/pw-browsers`; don't run
  `playwright install` there. Elsewhere (CI, a laptop): `npx playwright install --with-deps chromium`. The pinned
  `@playwright/test` (1.56.1) uses Chromium revision 1194, the one in `/opt/pw-browsers`.
- **check-precache** (`scripts/check-precache.mjs`) walks the import graph from each page's scripts, adds
  `new Worker()` targets, and diffs the result against `PRECACHE_ASSETS` in `sw.js`.

## How the tests work

- **Server:** `tests/serve.mjs` serves the repo root with real 404s. Playwright starts it on port 4173
  (`reuseExistingServer`, so a server already on that port is reused).
- **Stubs** (`tests/helpers.mjs`): every request that leaves localhost is intercepted.
  - PapaParse comes from `tests/node_modules`, pinned to the 5.4.1 the pages load.
  - html2canvas (the image exports) is aborted like any other CDN script, except in `export-flex.spec.mjs`, which
    serves it from `tests/node_modules`, pinned to the 1.4.1 the pages load (improvements F5).
  - Sleeper API calls are answered from `tests/fixtures/sleeper/*.json`, generated by
    `node tests/fixtures/sleeper/make-fixtures.mjs`: a 2-team "Fixture League" for user `mds_test`, 2026 week 2,
    with six free agents and week-2 matchups. **Edit the generator, not the JSON.** A Sleeper URL with no fixture
    gets a 404 and is recorded in `unmocked`; the MLS sync test asserts that list is empty, so a new endpoint fails
    loudly until you add a route in `SLEEPER_FIXTURES` and a file in the generator.
  - Everything else (Google Fonts, MathJax, Ko-fi, FantasyCalc, Google Sheets, headshots) is aborted.
    `/api/ffc/*` (the Pages Function in `functions/`) isn't run by `serve.mjs`, so it 404s unless a spec stubs it
    (`stubFfc` in `mds-sync.spec.mjs`).
- **Fixed clock:** 2026-09-15T16:00Z, so "Updated 3 days ago" labels and season logic don't drift.
- **What fails a test:** any uncaught exception, any `console.error`, any local HTTP status ≥ 400, or the fatal
  boot banner (`#mds-boot-error`). `openApp()` checks right after load, so a broken import names the missing file.
- **Seeded states:** `seedMds()` pastes `fixtures/rankings.csv` (24 players), saves it from the upload preview and
  makes 5 picks. `seedMls()` syncs the fixture league. `loadMlsRankings` uploads MLS rankings; `seedSimRandom`
  seeds `Math.random` so simulator numbers can be pinned. Pre-change storage snapshots live in
  `tests/fixtures/pre-6b/` and `tests/fixtures/pre-9a/` (each spec's header says how they were made).
- **`callApp(page, name, ...args)`** calls a function the page's entry module exports (`js/mds/main.js` on `/`,
  `js/mls/main.js` on `/lineup/`). It `import()`s the same URL the page loaded, so it gets the page's own module
  instance and runs exactly what the buttons run; nothing needs to be on `window`. To call a new function from a
  test, export it from that `main.js`. `showTab(page, id)` uses it. On T-Score, `showTScoreTab` clicks the tab's
  nav button.
- **Unit tests** (`tests/unit/`) import app modules by relative path. MLS modules that pull in the whole page can
  be loaded with the resolve-hook stubs in `tests/unit/helpers/playersEnv.mjs` (LOG 9C).
- **Widths:** every Playwright test runs twice, as `desktop` (1280×900) and `phone` (390×844, touch).

### Screenshots

- `visual.spec.mjs` takes 20 screenshots per width (40 PNGs) into `tests/baselines/linux/{desktop,phone}/`.
- **Tolerance** (owner's decision after 0C, in `playwright.config.mjs`): any colour change counts
  (`threshold: 0`) and at most 10 pixels may differ per PNG (`maxDiffPixels: 10`). Don't loosen it without the
  owner.
- **Repeatable rendering:** every screenshot is pixel-identical from run to run, thanks to two things. Keep both in
  any new screenshot code:
  - **Full raster:** `visual.spec.mjs` launches Chromium with `--disable-partial-raster` (0C). Partial raster
    left tiles of a page half-drawn on some runs.
  - **Parked mouse:** `shot()` moves the mouse to (0, 0) before each capture (8D). After a click, a re-render can
    put a new element under the pointer, and whether its `:hover` style makes it into the PNG depends on timing.
  - `tests/hide-transient.css` hides what depends on timing rather than on the code (the toast); animations are
    disabled and the caret hidden.
- **Baselines are Linux only.** Google Fonts is blocked, so text uses the OS's fallback fonts, and only the Linux
  ones are committed (`baselines/linux/`). On Windows (or macOS), Playwright finds no baselines for that OS: run
  `npx playwright test --ignore-snapshots` there, which still runs every test and skips only the pixel comparisons,
  and leave screenshots to CI and the cloud sessions. A plain run fails and writes `baselines/win32/` (or
  `darwin/`); `.gitignore` keeps those out of commits. CI runs on
  ubuntu-24.04 with Playwright's `--with-deps` font set, the same fonts as the cloud sessions.
- **The rendering environment is checked** (`tests/render-env.mjs`, 10A). `BASELINE_ENV` there records what the
  Linux baselines were made with: Playwright 1.56.1 (Chromium revision 1194) on Ubuntu 24.04. On Linux,
  `visual.spec.mjs` fails before taking any screenshot if this machine differs, naming what changed, and CI checks
  it in its own step ("Rendering environment matches the baselines", which also prints both, plus the runner
  image). `cd tests && node render-env.mjs` shows the same locally. The runner image's weekly version isn't
  checked; if CI's screenshots ever fail with the check green, compare the fonts first.

### Upgrading Playwright or the CI runner

A new Playwright version brings a new Chromium, and a new Ubuntu brings other fonts, so either changes how text
renders. Do it as its own PR, with no app changes in it:

1. Change the version (`@playwright/test` in `tests/package.json`, then `npm install` to update the lockfile) or
   the runner (`runs-on` in `.github/workflows/check.yml`).
2. Update `BASELINE_ENV` in `tests/render-env.mjs` to match.
3. Re-take every baseline in a cloud session: `npx playwright test visual.spec.mjs --update-snapshots=all`. First
   check that `/opt/pw-browsers` has the new Playwright's Chromium revision (`ls /opt/pw-browsers`); if it doesn't,
   the cloud sessions can't render the new baselines yet, and upgrading would leave them unable to run the
   screenshot tests. For a runner change, the cloud sessions must run the same Ubuntu, or the two will disagree.
4. Check the PNGs by eye (`npm run pxdiff -- <old> <new> --crops <dir>` against a copy of the old ones): only
   text and anti-aliasing should move. Then `npm run pxdiff -- --runs 5` to confirm the new renders repeat.
5. Push and make sure CI's screenshots pass too before merging.

### Accepting an intended visual change

A change that isn't meant to be visible must leave every screenshot identical. If yours *is* meant to change how
something looks:

1. `cd tests && npm run test:update`. It rewrites only PNGs whose comparison fails, so a change of 10 pixels or fewer
   can be left out. If yours might be that small, run
   `npx playwright test visual.spec.mjs --update-snapshots=all` and keep only the PNGs your change explains
   (`git checkout -- <png>` for the rest).
2. `npm run pxdiff -- --runs 1 --crops <dir>` lists exactly the PNGs your change touches, with side-by-side crops.
   Anything else it lists means rendering has become unrepeatable again: that's a bug to fix, not drift to accept.
3. Look at each changed PNG, then list them (and why) in your commit message or PR.

**When your machine can't reproduce the baselines** (Claude Code cloud sessions since 2026-10-03, whose image adds
fonts and font rules CI doesn't have; see docs/improvements/LOG.md, F1 and S9): render main and your branch the same
way there and compare them with `npm run pxdiff` to find the PNGs your change touches. Push without re-taking them, and
let the PR's CI fail on exactly those. Then take CI's renders from the run's `playwright-results` artifact:
`gh run download <run-id> -R btrerise/My-Draft-Strategist -n playwright-results -D <new empty folder>` works from
cloud sessions. Before committing an `-actual.png` as the baseline, check that its `-expected.png` is identical to the
committed baseline, and that the new image differs only where your change is.

### The opt-in tools

- **`npm run compare-css`** (`tests/tools/css-compare.tool.mjs`, 4D): renders the pages in several states from
  `origin/main` (or `COMPARE_REF=<ref>`, which must be from after refactor 5D) and from the working tree, and
  compares every element's computed style. Use it for any CSS change that must not be visible (moving or deleting
  rules, renaming classes): it catches differences a screenshot can't show, such as a hover or focus style.
- **`npm run pxdiff`** (`tests/tools/pxdiff.mjs`, 0C): `npm run pxdiff -- <dirA> <dirB> [--crops <out>]` counts
  the pixels whose RGB differs between two folders of PNGs, with the bounding box. `npm run pxdiff -- --runs 5`
  renders `visual.spec.mjs` five times, keeps each run's PNGs, puts the baselines back, and reports any run that
  differs. Use it when a screenshot fails unexpectedly, to tell a real change from flakiness.
- `tests/tools/playwright.config.mjs` matches `*.tool.mjs`, so the default config never runs these.

## Conventions

- **Service worker cache** (`sw.js`, its header has the rules):
  - Every JS and CSS file the pages load must be in `PRECACHE_ASSETS`. Adding, renaming or deleting one means
    updating the list in the same commit; `cache.addAll` fails all-or-nothing and silently. check-precache catches
    a mismatch.
  - Bump `CACHE_NAME` on every deploy that changes a file the site serves. Last number for every deploy, once per
    branch and above `main`'s (update to the latest main right before pushing); middle number only when the service
    worker's own behavior changes. A change only to tests, docs or tooling needs no bump.
  - `sw.js` stays at the site root, and the public URLs `/`, `/lineup/` and `/t-score/` don't change.
- **Script order:** every page loads `js/boot.js` first (a plain script), then `js/shared/globals.js`, then its
  entry module. In MLS, `js/mls/main.js`'s import list sets the module load order (LOG 3F); code that runs at a
  module's top level must not use names from modules that evaluate later.
- **Where CSS goes** (4D): one app only → `css/mds.css` or `css/mls.css` (T-Score: `css/tscore.css`); both apps,
  or a feature meant to be shared → `css/base.css`. An app-feature rule that has to beat earlier shared rules goes at
  the end of base.css. Before moving or deleting rules, run `npm run compare-css`.
- **No inline handlers** (5A): markup uses `data-action="name"` plus `data-*` attributes for arguments, and the
  page's entry module handles it with `delegate()` from `js/shared/ui/delegate.js`. Read that file's header before
  using it (capture phase, `event.currentTarget` is the container, detached elements).
- **Storage keys** (6A): every localStorage key and IndexedDB database is spelled only in
  `js/shared/storage/keys.js`; code reads it from `KEYS`. A new key starts with its app's prefix (`mds_` for Draft
  Strategist, `mls_` for Lineup Strategist) or it silently drops out of that app's backups. Never rename or remove a
  key casually: users' saved data lives under those exact strings. `js/boot.js` keeps its own copy of the
  ownership filters (checked by `tests/unit/bootKeyFilters.test.mjs`).
- **Bye weeks** (7C): only from `getByeWeek` in `js/shared/data/byes.js`, regenerated each May with
  `node scripts/update-byes.mjs <season>` (see the README).
- **Icons are SVG, never emoji** (owner's rule, improvements S1): any icon users see is an inline `<svg
  aria-hidden="true">` drawn with `stroke="currentColor"` (the existing icons are Feather-style, 24×24 viewBox), so it
  follows the theme and renders the same on every OS. Plain text symbols already used as glyphs (✕ on close buttons, ★)
  are fine; emoji (🔥, 🎉, 🔴) are not. `tests/unit/noEmoji.test.mjs` scans every served file (pages, `js/`, `css/`,
  `functions/`, comments included) for characters that render as emoji and fails naming the file and line.
- **User-visible changes** (8A): add a plain-language line under the app's **Unreleased** section in
  `CHANGELOG.md`. Bumping an app's footer version (the `APP VERSION` comment in `index.html` or
  `lineup/index.html`) turns those lines into that version's entry.
